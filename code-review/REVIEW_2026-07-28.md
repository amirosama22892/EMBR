## Findings

### Backend

### [MEDIUM] Single-threaded server + blocking body read — `embr-server.py:2359`, `:2268`
- [x] Fixed

**Fixed (2026-07-28):** Switched `socketserver.TCPServer` -> `http.server.ThreadingHTTPServer` (`daemon_threads=True`) and set a 30 s per-request socket timeout, so one slow/partial client can no longer stall the service. Verified: 8 concurrent calcs served in 0.01 s.

**What was tested:** Code trace of `socketserver.TCPServer` (single-threaded) plus `self.rfile.read(length)` with no socket timeout.

**What happened vs. expected:** The server processes one request at a time. A client that sends `Content-Length: 100` but only 10 bytes (and holds the connection) makes `rfile.read(100)` block indefinitely, stalling every other user — a slowloris-style stall. Expected: concurrent requests and/or a timeout so one slow client can't freeze the service.

**Why it matters:** Backend checklist §2/§3 (failure modes, concurrency). The input-validation hardening removed the *unbounded-compute* DoS, but the transport-level stall remains.

**How to reproduce:** `printf 'POST /api/calculate HTTP/1.0\r\nContent-Length: 100\r\n\r\n{}' | nc <host> 8080` and leave it open; a second request on the same server does not get served until the first times out (it won't).

**Suggested fix:** Use `http.server.ThreadingHTTPServer` instead of `socketserver.TCPServer`, and set a request/socket timeout (e.g., `timeout = 10` on the handler or server). Threading also makes the multi-user internal case behave.

### [LOW] Wildcard CORS on all JSON responses — `embr-server.py:2322`, `:2345`, `:2351` — (held: bug-review #11)
- [x] Fixed

**Fixed (2026-07-28):** Removed the wildcard `Access-Control-Allow-Origin: *`. EMBR is now same-origin only by default (no ACAO header); an optional `EMBR_ALLOWED_ORIGIN` env var re-enables a single explicit origin later without shipping open CORS. Regression-tested in `test_input_validation.py`.

**What was tested:** Every response sets `Access-Control-Allow-Origin: *`.

**What happened vs. expected:** Any website in a user's browser can script cross-origin calls to a running EMBR instance and read results. Low impact (read-only, no auth/session/secrets), but it's an unconsidered default. Expected: a conscious allowlist (e.g., the app's own origin) or an explicit decision to keep it open.

**Why it matters:** OWASP ASVS L1 hygiene (testing-standards §5).

**How to reproduce:** From any other origin, `fetch('http://<embr-host>/api/calculate', {...})` succeeds and returns readable JSON.

**Suggested fix:** Set the origin to the deployed app origin (configurable via env), or document the open-CORS decision. Deferred pending your walkthrough.

### [LOW] Serves the entire launch directory with listings — `embr-server.py:2249`
- [x] Fixed

**Fixed (2026-07-28):** Replaced open static serving with a servable-path allowlist (`/embr.html`, `/gridworks_logo.png`, `/favicon.ico`, `/docs/*.pdf`, plus `/docs/screenshots/*.png|jpg|webp` for the home-page carousel) and disabled directory listings; source files (`embr-server.py`, `requirements.txt`, ...) and `..` traversal now return 404. Regression-tested in `test_input_validation.py`.

**What was tested:** `AmpacityHandler(SimpleHTTPRequestHandler)` with no `directory=` argument.

**What happened vs. expected:** The process CWD is served recursively, including directory listings, not just the intended assets (`embr.html`, `/docs/*`, logo). Not path traversal (stdlib blocks `..`), but if ever launched from a directory containing more than intended files, they're exposed. Expected: serve only the intended asset set / no directory listings.

**Why it matters:** OWASP ASVS L1 (unintended exposure).

**How to reproduce:** `GET /` returns the app, but `GET /<any-other-file-in-cwd>` also serves it; a directory path returns a listing.

**Suggested fix:** Pass `directory=` pinned to the app folder and/or override `list_directory` to 404. Pairs with the CORS decision (#11). Deferred pending walkthrough.

### [LOW] Convergence loops give no non-convergence signal — `embr-server.py:653`, `:1211`, `:1415`
- [x] Fixed

**Fixed (2026-07-28):** Added a `for...else` to all three thermal-iteration loops that raises `ValueError` if 80 iterations pass without converging, instead of silently returning the last iterate (surfaces as a 500 rather than a wrong answer). TB 880 numerics unchanged.

**What was tested:** The three `for iteration in range(80):` self-consistency loops assign `theta_c = theta_new` unconditionally and return whether or not they converged.

**What happened vs. expected:** If a (currently unknown) input failed to converge in 80 iterations, the engine would silently return the last iterate as if converged. Expected: detect non-convergence and surface it (flag/error). No non-converging input was found during review — this is a missing safety net, not a demonstrated failure.

**Why it matters:** Backend checklist §2 (silent-wrong-answer failure mode).

**How to reproduce:** Not reproducible with known inputs; flagged for defensiveness.

**Suggested fix:** Track a `converged` boolean (break sets it true); if false after the loop, return an error/flag rather than a silent result.

**Fixed (2026-07-28):** Added `test_frontend.js` (jsdom, 17 integration tests) covering module nav, the input-handling fixes, and every finding below; wired into CI (`deploy.yml`, Node step). jsdom is a dev-only dependency, not shipped to Azure.

**What was tested:** Repo scan (`frontend.test_files: 0`) and manual confirmation that the frontend logic (`csz`, `mvOD`, `showModule`, `syncSoil`, `calculate()` error handling) is exercised only by ad-hoc jsdom snippets run during dev sessions — nothing committed, nothing in CI.

**What happened vs. expected:** The bugs just fixed (`parseInt||3` index-0, `MV_CABLES` crash) have no committed regression test, so they could silently reappear. Expected (Testing Trophy, testing-standards §1): a small committed integration suite over the golden path and the fixed cases, ideally in CI.

**Why it matters:** Testing Trophy — the frontend is the primary UI (926 lines) and its highest-value tests are integration-level, of which there are currently zero.

**How to reproduce:** `ls` the repo — no `*.test.*` / test file for the frontend; `deploy.yml` runs no frontend tests.

**Suggested fix:** Add a small jsdom (or Playwright) suite asserting: module switching, conduit-index-0 handled, bad-cableSize config doesn't crash, and a mocked-fetch error path surfaces in `#errorBox`. Wire into CI next to the Python suites.

### [MEDIUM] No request sequencing/debounce on `/api/calculate` — `embr.html:644`, `:676`, `:685` — (held: bug-review FE #3)
- [x] Fixed

**Fixed (2026-07-28):** Added a debounced (`scheduleCalculate`, 150 ms) latest-wins scheme with a monotonic request token (`_calcSeq`); a slow earlier response is now discarded rather than overwriting a newer one. Covered by frontend test FE-2.

**What was tested:** `onAnyChange` fires a `fetch` on every `input`/`change` across ~40 fields with no debounce, `AbortController`, or sequence check.

**What happened vs. expected:** Under real latency variance, an earlier request's response can resolve after a later one and overwrite the results panel with stale numbers, with no indication. Expected: latest-wins (debounce + abort, or a sequence token).

**Why it matters:** Frontend checklist §2/§3 (rapid input, out-of-order responses).

**How to reproduce:** Throttle the network, change an input twice quickly; the panel can settle on the first response's value.

**Suggested fix:** Debounce `calculate()` (~150 ms) and use an `AbortController` (abort the prior in-flight request) or a monotonically increasing request id, applying only the newest.

### [LOW] Server-echoed values rendered via `innerHTML` — `embr.html:656`, `:673` — (held: bug-review FE #5)
- [x] Fixed

**Fixed (2026-07-28):** `rInfo` and the detail-grid cards are now built with `textContent`/DOM nodes instead of string-concatenated `innerHTML`, so server-echoed values can never be parsed as markup. Covered by frontend test FE-3 (an injected `<img>` renders as text).

**What was tested:** `$('rInfo').innerHTML = r.cableLabel + '<br>' + ... + r.phaseConfig` and the detail-grid build concatenate server strings into HTML.

**What happened vs. expected:** Not exploitable today (the server now enum-validates these fields), but it's latent reflected-XSS if any of those fields ever widens to free text. Expected: render text as text.

**Why it matters:** OWASP ASVS L1 (output encoding).

**How to reproduce:** Not currently reproducible (values enum-constrained); latent.

**Suggested fix:** Build these nodes with `textContent` (and explicit `<br>`/elements) instead of string-concatenated `innerHTML`.

### [LOW] Custom soil-preset dropdown not keyboard-operable — `embr.html:372` (soil menu)
- [x] Fixed

**Fixed (2026-07-28):** Added `role=menu`/`menuitem`, `aria-haspopup`/`aria-expanded`, focus-into-menu on open and return-to-toggle on close, and Arrow/Home/End/Escape key handling. Covered by frontend test FE-4.

**What was tested:** The Native/Dry-Out ρ fields use a custom ▼ menu (a `<button>` toggling a `<div>` of option `<button>`s), reviewed statically + jsdom.

**What happened vs. expected:** The menu opens on click and closes on outside-click, but there's no arrow-key navigation, no Escape-to-close, and no focus management/ARIA. A keyboard-only user can't operate it the way a native `<select>` allows. Expected: keyboard operability + `aria-expanded`/roles.

**Why it matters:** WCAG 2.2 Operable / keyboard (testing-standards §3).

**How to reproduce:** Tab to the ρ field, try to open/choose a preset with the keyboard only.

**Suggested fix:** Add keydown handling (↑/↓/Enter/Escape), move focus into the menu on open and back on close, and set `role="listbox"`/`aria-expanded`. (Typing a value already works, so this is degraded-but-not-blocked.)

### [LOW] Soil-lookup fetches skip `response.ok` — `embr.html:737`, `:774` — (held: bug-review FE #7)
- [x] Fixed

**Fixed (2026-07-28):** Both Open-Meteo fetches now check `r.ok` and throw (routing to the existing `.catch` that shows the API error) instead of treating a non-2xx as empty data. Covered by frontend test FE-5.

**What was tested:** The Open-Meteo geocode/archive fetches call `.then(r => r.json())` without checking `r.ok`.

**What happened vs. expected:** A non-2xx JSON error from Open-Meteo is treated the same as "no data" rather than surfacing the real API error. Failures are caught so nothing hangs. Expected: distinguish an API error from empty results.

**Why it matters:** Frontend checklist §2 (error states reachable/readable).

**How to reproduce:** Force a 4xx/5xx from the Open-Meteo endpoint; UI shows a generic no-data state.

**Suggested fix:** Check `r.ok` and show the API error message; low priority (external, user-initiated).
